## 上下文工程

- agent status bar

状态栏位于每轮循环上下文的最后，并且`role: user`

```ts
messages: [
  { role: "system",    content: "You are a customer service assistant..." }  ← Fixed (KV Cache cached)
  { role: "user",      content: "Help me cancel my Xfinity plan" }  ← Original user request
  { role: "assistant", content: null, tool_calls: [...] }   ← Round 1: model decides to call
  { role: "tool",      content: "Call log..." }             ← Round 1: call result
  { role: "assistant", content: null, tool_calls: [...] }   ← Round 2: model decides to call again
  { role: "tool",      content: "Call log..." }             ← Round 2: call result
  ...(more rounds)
  { role: "user",      content: "Can you call them again to follow up?" }  ← User follow-up
  { role: "user",      content: "<agent_status>             ← Status bar injected by Agent framework
      Current State:                                           (as a user message)
      - phone_call invoked 3 times (Xfinity: 3/3 max)
      - Current time: 2025-09-14 10:30:45
      - TODO: [1] Cancel plan (in_progress)
    </agent_status>" }
]
```

状态栏的本质也是一种上下文压缩的方式，通过把学要思考的结论变成可以直接检索的知识，这揭示了上下文压缩的设计原则：与其期望模型从冗长的上下文中自动学习，不如主动地、显式地进行知识提炼。虽然需要额外的计算投入（用专门的 LLM 调用来做总结），但产生的是经过压缩的高密度知识表示——**不要让模型被动地在海量信息中检索，而要主动为模型提供经过提炼的结构化知识**。

- 子agent上下文隔离

  作为同样是一种管理上下文的方法，隔离的优先级大于压缩上下文

| 对比               | Agent Status Bar                 | 子 Agent 上下文隔离              |
| ------------------ | -------------------------------- | -------------------------------- |
| 核心思路           | 提炼当前任务的关键状态           | 将不同任务的上下文分开           |
| 解决的问题         | 历史太长，重要状态不容易被注意到 | 不同任务共享过多无关信息         |
| 常见手段           | 状态摘要、动态注入               | 独立消息历史、任务输入与结果传递 |
| 是否必然减少 Token | 不一定                           | 也不一定，但可以避免复制大量历史 |

#### 五个信息管理策略，四个具体的实现机制

-  **保留：Keep**

对当前任务仍然有用的信息直接保留。例如当前正在修复的报错、相关文件内容、最近一次测试结果。这是最简单的手段：有用的信息不应该为了省 Token 被随意删除。

-  **压缩：Compress**

将大量历史转换为更短、但仍然保留关键事实的摘要。例如把十轮调试记录压缩成：「问题是 `ToolLoopAgent` 的子 Agent 类型不兼容；已确认工具调用正常，当前需要检查类型定义。」这里不是简单删掉前面的消息，而是提取对后续决策有用的信息。

- **检索：Retrieve**

不把所有历史都放在当前上下文中，而是先保存到外部存储，需要时再查找。例如以前讨论过 `pruneMessages`、Mem0 或上下文隔离。现在需要相关信息时，检索对应记录即可。这是 RAG 思想在 Agent 历史管理中的一种应用。

- **隔离：Isolate**

不同任务维护不同的上下文。例如，搜索子 Agent 只接收搜索目标和必要的项目背景；代码探索子 Agent 接收需要调查的模块和允许使用的工具。子 Agent 返回有价值的结果后，主 Agent 再选择性地接收，而不是共享所有内部过程。

- **优先级与预算：Prioritize**

当上下文空间有限时，按照信息的重要程度分配 Token。例如，当前用户目标、关键约束、最近的工具结果、待完成事项，通常比很久以前的一段闲聊更值得保留。

-----

1. **Pruning：剪裁**

直接减少上下文内容

比如历史里有 30 轮对话，当前只需要最近几轮，以及更早的架构约束。你可以删除无关消息，或者移除冗长的工具输出。特点是直接、快速，但如果删除了关键事实，后续任务可能出错。

2. **Summarization：摘要压缩**

用更少的文字保留重要信息，例如把 10 轮调试记录总结为：

> 已定位到 `ToolLoopAgent` 的类型不兼容问题；工具执行正常；尚未解决的是子 Agent 的类型定义。

3. **Status Bar：状态栏 / 工作状态**

显式维护当前任务状态

```txt
当前目标：修复子 Agent 类型错误
已完成：定位类型不兼容的位置
当前状态：正在检查类型定义
待完成：修复类型并运行测试
约束：不修改现有工具接口
```

状态栏与摘要的区别在于：摘要通常是对过去的概括；状态栏则强调当前有效状态，并应随着任务推进而更新。它不一定要显示在用户界面上，也可以是内部维护的工作状态。

4. **Context Isolation：上下文隔离**

为不同任务建立不同的上下文边界

比如搜索子 Agent 负责查找相关代码，代码探索子 Agent 负责分析模块依赖。它们接收各自需要的信息，而不是无条件共享主 Agent 的完整消息历史。

#### 知识库构建：

Chunking:

**固定大小切分**：最简单的方法，按固定的 token 数（如 512）切分，通常在相邻块之间保留一定重叠（如 50-100 token），避免关键句子恰好在边界处被切断。实现简单、结果可预测，但完全无视文档结构——一个段落、一段代码、一张表格都可能被拦腰截断。

**递归/结构感知切分**：按文档的自然边界（章节标题、段落、句子）递归切分——先尝试按大边界切块，仍超长时再降级到更小的边界。Markdown、HTML 这类有显式结构的文档尤其适合。这是目前生产系统最常用的默认选择。

**语义切分**：计算相邻句子的嵌入相似度，在语义“断崖”处（相似度骤降的位置）下刀，使每个块内部主题尽量单一。切分质量更高，代价是需要额外的嵌入计算。

#### 知识的组织和检索

- 如何组织知识：(结构化索引)

`RAPTOR`:   树状层次，它首先将长文档切分为小的文本块作为“叶子节点”，然后通过聚类算法将语义相近的叶子节点分组——聚类类似于把图书馆的书按主题自动分堆：算法计算每本书（每个文本块）之间的相似度，把最相似的归为一类，每一类就代表一个主题。

`GraphRAG`：实体关系图，使用实体关系来组织知识

>结构化索引和前文的稠密嵌入，重排并不冲突，在文本量不大的情况下，使用结构化索引反而会使得llm调用次数增多从而导致了资源耗费增加

## Coding Agent

就一般面向开放性问题的通用agent，一般由coding agent和文件系统组成，coding agent一般包含七种基本工具：

1. **Code Interpreter（代码解释器）**：提供隔离的沙盒环境（sandbox，即与主系统隔离的安全运行空间，代码即使在其中运行出错也不会影响宿主机），安全执行 Python 代码
2. **Bash Shell（命令行终端）**：在终端中执行命令，如运行测试用例、处理特殊格式文件
3. **读文件工具**：读取代码、配置、文档、日志等
4. **写文件工具**：创建新文件或完全重写现有文件
5. **编辑文件工具**：对现有文件进行局部修改，是代码维护和迭代的核心操作
6. **搜索文件名工具（Glob）**：通过模式匹配快速定位文件系统中的目标文件，例如用 `**/*.py` 找出项目中所有 Python 文件
7. **搜索文件内容工具（Grep）**：在文件内容中搜索特定的文本模式，例如搜索所有调用了某个函数的代码行

#### coding agent的实现：

- 并行工具调用，流式执行与级联中止
- 上下文的精细管理

- 环境信息的动态注入

- 命令执行环境的状态持久化

- 即时的语法反馈机制

  



## Harness

| 层面                  | 组件       | 解决什么问题               |
| :-------------------- | :--------- | :------------------------- |
| **让 Agent 能做事**   | **上下文** | 模型每一步能看到什么信息   |
|                       | **工具**   | 模型能用什么手段去操作环境 |
| **让 Agent 不做错事** | **约束**   | 提前禁止某些错误行为       |
|                       | **验证**   | 判断产出到底对不对         |
|                       | **纠正**   | 错了之后怎么恢复或回滚     |

- 关于约束：约束要用代码强制执行，不要写在文档里“建议”

- 验证必须自动化
- 反馈越快，越结构化越好，这样agent的自我纠正效率越高

-------

**故障处理**

- **API 层**：限流（HTTP 429）、服务过载、请求超时、连接中断、输出触顶被截断。这类故障与任务内容无关，是基础设施的噪声。
- **工具层**：幻觉调用（调用了不存在的工具）、参数畸形（不符合工具的输入约束）、执行抛异常，以及最危险的一种——工具反复返回同一个错误，而模型不加改变地反复重试。
- **上下文层**：上下文窗口溢出、压缩失败、轨迹结构损坏（如工具调用缺少配对的结果消息）。
- **控制流层**：死循环（反复执行相同操作却毫无进展）与死亡螺旋（错误触发的恢复逻辑自身又调用 LLM、再次出错、连锁反应）。

对于错误处理：**先判断错误类型，再去决定恢复策略**

- 判断无效重复的方法：

  - 重复调用指纹：给工具调用添加指纹

  ​              fingerprint=tool name+normalized arguments

  ```ts
  { tool: "grep", args: { pattern: "TODO" } }
  
  ```

  - 统计失败次数

> 工具最好能够返回结构性错误，以方便后续的模型处理，但是也需要区别可恢复的业务错误和直接中止的系统错误（例如沙箱越权，严重的状态损坏等）

**恢复策略：**

1. 静默重试:
2. 改变策略
3. 明确报告失败

**跨模型接管：**

因为不同模型提供商的接口协议可能不同，因此再把当前的上下文作为信息注入到新的模型是可能出现不兼容的情况，对应的解决办法可以使用**中立轨迹格式**，然后在适配层转入对应模型需要的格式

```ts
type AgentEvent =
  | {
      type: "user_message";
      content: string;
    }
  | {
      type: "assistant_message";
      content: string;
    }
  | {
      type: "tool_call";
      toolName: string;
      args: Record<string, unknown>;
      callId: string;
    }
  | {
      type: "tool_result";
      callId: string;
      result: unknown;
    };
```

> 这里只是作为一个示例，可能还会包括错误信息等

## 通用agent的元能力

1. **思维本身**——用代码替代易错的自然语言推理（思考工具）；
2. **业务规则**——把模糊的政策编码为可执行约束（业务规则约束）；
3. **内容呈现**——生成 PPT、视频与可视化产物（多媒体生成）；
4. **系统接口**——桥接异构 API，自动适应数据格式演化（系统适配器）；
5. **用户界面**——动态构造表单与交互界面（生成式 UI）；
6. **Agent 自身**——用代码创造或修复新 Agent，形成自举。
